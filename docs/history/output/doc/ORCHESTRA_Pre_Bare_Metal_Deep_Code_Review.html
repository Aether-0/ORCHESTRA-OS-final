4. Ownership proof

  • Scheduling policy is per-thread; process leaders and worker threads can differ.
  • Non-opted tasks remain fair-class tasks.
  • The bridge can alter any explicit PID permitted to the caller.
  • PID reuse protection is weakened because the bridge publishes cookie zero.
  • The isolated P0 test provides credible aggregate ownership evidence; the general benchmark does not provide per-target proof.

6. P0 blockers

  1. Remove or synchronize the shared directive cache.
  2. Make two-slot publication coherent under reuse and concurrent writers.
  3. Eliminate broad bpffs deletion and all-struct_ops detach.
  4. Add deterministic cleanup and independent recovery.
  5. Verify link/map ownership before pinning or detaching.
  6. Reject RT, deadline, stale, reused, and unapproved target identities.
  7. Make ownership proof per-thread and per-run.
  8. Resolve partial-switch fairness for the experiment design.
  9. Reproduce the 7.7-second result under controlled VM instrumentation.
  10. Declare and reproduce the exact target kernel/API.
Gate rule: no physical performance benchmark until every item above has a retained passing VM result.

10. Concurrency/race analysis

  • The BPF cache is one shared ARRAY value, mutated field-by-field by concurrent CPUs.
  • The reader does not reread control after copying a directive.
  • Two writers can publish the same generation and inactive slot.
  • Clearing resets generation to zero, permitting cached generation reuse.
  • Simulator C11 publication tests do not validate this separate kernel protocol.
  • Positive: hot paths contain no unbounded loops and retain no task/map pointers across callbacks.

Why old Stage 8/9 performance claims are invalid

  • Attach was proven, but worker ownership was not.
  • Dispatch callback noise rose while owned enqueue/run stayed zero.
  • Historical 4-5% or about 20% overhead figures cannot be ORCHESTRA-versus-Linux evidence.

Why the corrected P0 benchmark is still diagnostic

  • Global cumulative counters are not per-run or per-PID.
  • Ownership failure does not terminate the script.
  • Sequential publication targets only the final worker.
  • Fixed-duration loops measure configured duration, not throughput.
  • The completion timer is asymmetric.
  • Context switches are system-wide.
  • No repeated, randomized, interleaved campaign exists.
Scientific rule: no positive per-target ORCHESTRA running evidence means the row is INVALID, not a zero-overhead success.

Metrics schema drift

The userspace binary emits metrics/v6 with 120 columns. The standalone validator understands v6, but the campaign runner, manifests, and committed JSON schemas stop at v5. VBox Phase B recorded this as a schema failure.

16. Safe bare-metal acceptance plan

1. Remediate and freeze
Fix all P0 items; declare exact kernel, source, BTF and object hashes.
2. Repeat VM gates
Verifier, ownership, crash, watchdog, detach, RT admission and 7.7-second investigation.
3. Prepare physical recovery
Known-good kernel, console/remote management, SysRq, second root shell, owned pin directory.
4. Attach only
Record state, register exact owned link, verify scheduler identity and state.
5. One disposable RUN task
Barrier-controlled TID, explicit identity and affinity, per-TID enable/running proof, seconds-long bound.
6. Clean detach
Detach exact ORCHESTRA link; verify state disabled, fair policy restored, no residual pins or kernel warning.
7. Expand cautiously
Repeated lifecycle, invalid fallback and YIELD. Performance and other actions remain later gates.

The existing real-world checklist remains the authoritative broad protocol. The first acceptance should use a documented subset, not create another competing checklist.

20. Final recommendation

Do not run the current repository benchmark scripts on a physical machine.

The sched_ext prototype is real and has crossed the VM ownership gate, but it is not yet safe or scientifically adequate for the planned bare-metal benchmark. Continue from the existing post-Stage-9 implementation; do not restart from simulation.

Next milestone: fix P0 concurrency, ownership, cleanup, admission, API and lifecycle issues; reproduce the 7.7-second regression in VM; then execute one narrowly bounded physical RUN acceptance test.
