4. Kernel architecture trace

bridge --opt-in PID/TID
  -> sched_setattr(pid, SCHED_EXT)
  -> partial-switch sched_ext ownership

task becomes runnable
  -> select_cpu()
  -> reads the existing shared cache before refresh
  -> orchestra_place()
       -> control map -> active slot -> directive map
       -> field-by-field shared-cache update
       -> PID/TGID/cookie/expiry checks
       -> action switch
       -> direct scx_bpf_dispatch()
  -> select_cpu() returns
  -> enqueue() is skipped after direct dispatch
  -> local DSQ / requested remote local DSQ
  -> running()
  -> slice consumption
  -> stopping()
  -> SCX_OPS_ENQ_LAST re-enqueue
  -> direct-dispatch cycle repeats

The direct-dispatch contract avoids an ordinary double dispatch: a successful dispatch in select_cpu() causes sched_ext to skip enqueue(). The empty dispatch() callback is viable only because every ordinary placement path directly dispatches the current task.

6. DSQ, CPU placement, slices and fairness

No custom or shared global DSQ is used. All work enters SCX_DSQ_LOCAL, except MIGRATE requests to SCX_DSQ_LOCAL_ON | cpu. There is no stealing, virtual runtime, weight, deadline, lag or bandwidth accounting.

ActionSliceOperational resultSemantic classification
RUN5,000,000 ns nominalLocal FIFO executionREASONABLE APPROXIMATION
YIELD1,000,000 nsStill receives a normal queue turnINCOMPLETE
SLEEP before deadline500,000 nsContinues to executeSEMANTICALLY WRONG
THROTTLE500,000 nsImmediate requeue, no duty-cycle windowSEMANTICALLY WRONG
MIGRATERequested or 5,000,000 nsRemote-local request counted before executionINCOMPLETE / UNSAFE

Among N tasks already assigned to one CPU, FIFO slices give approximate round-robin service. RUN versus THROTTLE is roughly 5 ms versus 0.5 ms per cycle, but shorter slices alone do not impose a bandwidth ceiling. In partial switching, any continuously runnable fair-class task can prevent all SCHED_EXT progress because Linux 6.12 orders fair above ext.

7. Task ownership analysis

  1. A directive can reach the wrong task through a mixed cache, generation ABA or PID reuse.
  2. PID reuse is not closed because the bridge publishes cookie zero.
  3. Leader-only opt-in does not opt in existing sibling threads.
  4. Future fork/clone descendants may inherit SCHED_EXT without independent bridge admission.
  5. Existing SCHED_NORMAL tasks are outside ORCHESTRA in partial mode, but inherited SCHED_EXT descendants are an exception to explicit bridge admission.
  6. running() proves only that some SCHED_EXT task ran, not which directive or CPU controlled it.

11. C implementation analysis

Memory and lifecycle

The canonical engine bounds allocations and mapped regions, closes key resources, uses an async-signal-safe handler, and reaps workers with bounded TERM/KILL escalation. The bridge's unvalidated map lookup is the primary memory-corruption risk: the kernel copies the map's actual value size into the supplied fixed-size userspace buffer.

Canonical publication and cryptography

The canonical transport uses explicit big-endian serialization, fixed 128-byte payloads, HMAC-SHA256, per-epoch keys, constant-time comparison, atomic generation tokens, alternating slots, reader pins, writer leases and copy/revalidation. It rejects schema, source, tier, sequence, future, stale, epoch and numerical errors. The live bridge does not use this transport.

Parsing and resource errors

The bridge uses atoi() for PID/CPU and unchecked strtoull() for time values. Its /proc/[pid]/stat parser advances past field 22 and reads field 23, then discards the value. cmd_clear() can leak one map FD and ignores slot/control write failures while reporting success.

12. Predictor, RL, S1-S4, Q and controller

The fixed-gain predictor follows the corrected offline-calibrated direction. Gain search covers 0.01 through 0.99 using true one-step-ahead squared error. Confidence is exp(-5 * forecast_error), and confidence below 0.50 selects observed state.

15. Dependency-ordered fixes

  1. Resolve fair-over-ext starvation and specify enforceable ownership/admission.
  2. Replace PID/TGID-only identity with lifetime-stable task identity.
  3. Bind the bridge to the exact BPF object and validate every map ABI.
  4. Remove/redesign the shared BPF cache.
  5. Serialize publishers and introduce a nonrepeating publication epoch.
  6. Unify or exhaustively translate the action ABI.
  7. Replace the singleton directive with strong-identity per-task directives.
  8. Make MIGRATE affinity-aware and prove success in attributed running().
  9. Implement true deferred eligibility and bandwidth accounting for SLEEP/THROTTLE.
  10. Correct userspace affinity restoration and RT admission.
  11. Make conditioned S3 canonical; make S2 sequence-current and S4 lifecycle-aware.
  12. Fix calibration arithmetic, policy persistence, CLI parsing and secure temporary files.
  13. Add per-task generation/action/CPU telemetry and restore or replace idle tracking.
  14. Recompile and verify against every explicitly supported sched_ext API version.

17. Final recommendation

No: the current prototype is not technically safe enough for the first controlled physical-machine test.

The canonical userspace signal publication core is comparatively sound and well tested. The live bridge and kernel scheduler, however, do not yet preserve bounded progress, strong task ownership, coherent publication or five-action semantics. Fix the K0 and C0 items first, complete post-fix verifier and VM tests, then repeat this gate review before any physical-machine run.
