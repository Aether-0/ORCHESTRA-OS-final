Source-only first pass

The scheduler skeleton is viable, and Linux sched_ext supplies a last-resort fallback when the BPF scheduler exits. The current source nevertheless permits stale task identity, incoherent directive reads, cross-CPU cache races, invalid migration requests, unsafe RT/deadline opt-in, and partial-switch starvation.

Decision: do not load this revision on a physical machine. First correct the K0 findings and repeat compile-only, verifier, and VM runtime validation against the exact target kernel.

2. Algorithm verdict

CONSISTENT WITH IMPLEMENTATION GAPS. The isolated canonical userspace mathematics is internally coherent. No standalone A0 defect was found.

Strong areas include aligned state/directive boundaries, a fixed-gain predictor that does not reintroduce the rejected adaptive-covariance Kalman design, correct epsilon annealing, directive-dominant rewards, bounded difference rewards, the four-factor geometric mean, and a genuinely slower outer controller.

The main defect is integration: prediction, RL, jitter, S1-S4, Q, and feedback control do not feed the live sched_ext bridge. The kernel is currently a manually driven, single-active-directive executor.

3. Kernel architecture trace

Task execution path

selected TID
  -> sched_setattr(SCHED_EXT)
  -> Linux partial-switch ownership
  -> orchestra_sched_select_cpu()
       -> consult shared cache
       -> choose previous or requested CPU
       -> orchestra_place()
       -> direct dispatch to LOCAL or LOCAL_ON DSQ
  -> enqueue() skipped after direct dispatch
  -> sched_ext core consumes local DSQ
  -> orchestra_sched_running() increments global counter
  -> task executes for requested slice
  -> orchestra_sched_stopping() performs no accounting
  -> block, wake, or slice expiry
  -> select_cpu()/enqueue() cycle repeats

Bridge-to-kernel path

orchestra_bridge publish
  -> write inactive bridge_directive_map slot
  -> read back generation and PID only
  -> replace bridge_control_map active slot/generation
  -> BPF copies fields into shared dir_cache_map
  -> PID/TGID/expiry/action checks
  -> action-specific slice and DSQ insertion request
The dispatch callback does not choose a task. The current scheduler depends on direct dispatch from select_cpu() or enqueue(). A request counter is not proof that the task reached CPU execution.

Publication race

reader: control pointer -> live slot pointer -> shared cache field copies
  • A reader can observe a logically mixed packed value.
  • The reader never copies and then revalidates control generation and slot.
  • Two publishers can choose the same inactive slot and generation.
  • clear resets generation, creating ABA reuse.
  • Cache hits compare generation only, allowing stale reuse.
  • The canonical userspace generation bus has reader gates; this BPF bridge does not.

7. DSQ and CPU-placement review

Only SCX_DSQ_LOCAL and SCX_DSQ_LOCAL_ON | cpu are used. There is no global ORCHESTRA DSQ, deferred-eligibility DSQ, budget-replenishment queue, priority structure, or explicit work stealing.

The sched_ext core prevents the normal direct-dispatch path from also invoking enqueue, so no ordinary double dispatch was found. Every current action inserts the task, so no intentional task-loss branch was found.

MIGRATE is not placement-safe in project code. It checks only CPU_ANY and nr_cpu_ids, not affinity, online/active state, hotplug, or migration-disabled state. Linux performs a final safety check, but rejection can cause fallback or a sched_ext operations error rather than a successful migration.

The code targets the Linux 6.12 legacy scx_bpf_dispatch() interface. sched_ext is intentionally unstable; compilation against another kernel is not semantic proof. See the current sched_ext documentation and Linux v6.12 sched_ext implementation.

9. Fairness/starvation analysis

ORCHESTRA has no vruntime, service lag, task weight, deadline, or accumulated-runtime fairness accounting. Per-CPU FIFO order plus slice length is the full model.

PopulationExpected behaviorFailure mode
1 RUN taskRepeated 5 ms dispatch; near-full CPUUnnecessary callback/requeue churn.
2 identical RUN tasksApproximate 5 ms FIFO round robinNo Linux weight semantics.
N CPU-bound tasksApproximate local share of 1/NcpuPersistent local imbalance; idle CPUs may coexist.
RUN + YIELDApproximate 5:1 slice serviceYIELD alone still consumes 100% CPU.
RUN + THROTTLEIncidental 10:1 slice ratioTHROTTLE alone still consumes 100% CPU.
RUN + MIGRATEMigrant requested on target local queueTarget overload, invalid affinity, or fallback unobserved.

In partial mode, conventional fair-class tasks have higher precedence than ext tasks. Without admission and CPU isolation, a continuously runnable fair task can starve ORCHESTRA until watchdog recovery detaches the scheduler.

10. Predictor review

forecast_t   = estimate_(t-1)
innovation_t = observation_t - estimate_(t-1)
estimate_t   = clip(estimate_(t-1) + K * innovation_t)
  • Gain is grid-calibrated from 0.01 through 0.99 before worker evaluation.
  • Calibration computes true one-step-ahead error before each observation update.
  • No runtime covariance adaptation exists; the rejected adaptive Kalman design was not reintroduced.
  • State and output are clipped to [0,1].
  • Low confidence or non-finite prediction falls back to observed CPU.

Confidence is exp(-5 * previous_absolute_error). The 0.5 fallback threshold corresponds to error above about 0.1386. This is safe as a bounded heuristic but is not calibrated forecast uncertainty.

Calibration is temporally separated but not a versioned, independently held-out workflow tied to workload and hardware metadata. The runtime estimate is used immediately and behaves more like a filtered nowcast than an explicit horizon-bearing forecast.

11. RL/adaptive-policy review

Directive regions

Condition, in priority orderDirective
thermal > 0.90 or CPU > 0.94THROTTLE
otherwise CPU > 0.82 or memory > 0.90MIGRATE
otherwise CPU > 0.68YIELD
otherwise CPU < 0.20SLEEP
otherwiseRUN

The 5 CPU buckets, 2 memory buckets, and 3 thermal buckets create 30 states. Every boundary aligns with the directive function; no state crosses a canonical action boundary.

Q(s,a) <- Q(s,a) + 0.20 *
          [reward + 0.90 * max Q(s',a') - Q(s,a)]

Epsilon is max(0.02, 0.30 * 0.998^sequence) and reaches the floor near sequence 1,353. Decay is global per publication sequence, not per successful agent update.

Local reward is +0.6 for the directive action and -0.6 otherwise. Exhaustive bounds preserve directive dominance after switching and difference-reward terms. The optimized difference reward uses a YIELD counterfactual, clips to [-0.6,0.6], blends at 0.30, and runs in O(N*A), not O(N^2).

13. Anti-synchronization review

sigma = MAD(first differences) * 1.4826 / sqrt(2)
jitter_floor = min(0.20, 1.5 * sigma)

The sqrt(2) correction is correct for independent observation noise in first differences, and MAD is robust against isolated spikes. Workload dynamics can nevertheless inflate the estimate.

  • Each agent has a privately seeded Gaussian stream.
  • Perceived CPU is clipped to [0,1].
  • Jitter can split agents around CPU thresholds.
  • Memory and thermal thresholds are not privately perturbed.
  • The controller can raise jitter to 0.20 without a joint S2/S4 compliance guard.

15. Kernel to algorithm mapping

Action ABI mismatch: canonical userspace uses RUN=0, SLEEP=1, MIGRATE=2, THROTTLE=3, YIELD=4. The bridge uses RUN=0, YIELD=1, MIGRATE=2, THROTTLE=3, SLEEP=4.

Scenario A - low CPU load

With old estimate 0.12, observed CPU 0.10, and gain 0.90, the new estimate is 0.102. With adequate confidence, CPU below 0.20 selects SLEEP. The userspace demo performs nanosleep. No automatic bridge publication exists; manual kernel SLEEP instead dispatches repeated 0.5 ms slices.

Scenario B - overload threshold crossing

CPU prediction 0.85 with lower memory and thermal signals selects MIGRATE. Numeric value 2 matches both ABIs. The bridge publishes a target, BPF requests LOCAL_ON, and Linux may reject or redirect an invalid target. The BPF increments its effective counter before running() observes the CPU.

Scenario C - synchronized herd risk

A CPU transition from 0.680 to 0.681 changes RUN to YIELD. Private jitter should split agents around the threshold. If all switch, historical S4 becomes zero. At the first controller update, beta is about 0.014142; jitter rises by about 0.00283 and switching penalty by about 0.00212. None of this controller state reaches BPF today.

HMAC, floating point, logarithms, exponentials, population scans, difference rewards, consensus, and controller analytics should remain outside BPF. The hot path should validate immutable identity, generation, freshness, action ABI, and CPU legality; enforce bounded dispatch/budget behavior; and emit correlated outcome events.

18. K0 findings

K0 K0-01 - Reusable task identity

Area
Task ownership
File / function
orchestra_bridge.c:get_task_info(), cmd_publish(); orchestra_scx_stage7.bpf.c:bridge_directive_valid()
Problem
Directives are bound only to reusable PID/TGID values.
Why it is wrong
Cookie zero disables task-instance validation, and the proc parser reads field 23 rather than starttime field 22.
Possible runtime effect
A stale directive controls a different task after PID/TID reuse.
Evidence
BPF treats zero cookie as no check; directives remain valid until expiry.
Required fix
Require a correctly parsed immutable task cookie, reject zero for targeted directives, and bind all per-task state to it.

K0 K0-02 - Unsynchronized global directive cache

Area
Cross-CPU concurrency
File / function
orchestra_scx_stage7.bpf.c:bridge_refresh_cache(), bridge_cached_directive()
Problem
One global cache value is field-by-field read and mutated by callbacks on every CPU.
Why it is wrong
No lock, per-CPU ownership, sequence protocol, or coherent copy exists.
Possible runtime effect
Mixed identity, action, target CPU, expiry, or generation fields.
Evidence
dir_cache_map is a one-element shared ARRAY.
Required fix
Use a validated immutable per-callback snapshot or per-CPU cache sourced through a retryable sequence protocol.

K0 K0-03 - Incoherent publication and generation ABA

Area
Directive publication
File / function
orchestra_bridge.c:cmd_publish(), cmd_clear(); orchestra_scx_stage7.bpf.c:bridge_refresh_cache()
Problem
The two-slot protocol is not a coherent snapshot and resets generations.
Why it is wrong
Map copies are not multi-field transactions; readers do not revalidate; slots and generations are reused; publishers are unserialized.
Possible runtime effect
New generation with old data, old generation with overwritten data, or stale cached action reuse.
Evidence
Readback checks only generation and PID; cache hits compare only generation.
Required fix
Serialize publishers, use never-reset 64-bit epochs, copy and revalidate control/slot, retry on change, and validate all fields.

K0 K0-04 - Unsafe migration request

Area
CPU placement
File / function
orchestra_scx_stage7.bpf.c:orchestra_place(), orchestra_sched_select_cpu()
Problem
MIGRATE does not validate affinity, online/active state, hotplug, or migration-disabled state.
Why it is wrong
Linux prevents illegal execution but can reject the request through fallback or a scheduler operations error.
Possible runtime effect
Scheduler detach, unexpected fallback placement, or false migration success.
Evidence
Only CPU_ANY and nr_cpu_ids are checked; success is counted before running().
Required fix
Validate against allowed and online masks, handle races safely, and confirm the request generation and actual CPU in running().

K0 K0-05 - RT/deadline policy destruction

Area
Hybrid Safety Layer
File / function
orchestra_bridge.c:cmd_optin()
Problem
The bridge can replace a real-time or deadline scheduling policy with SCHED_EXT.
Why it is wrong
No admission check or deterministic-class exemption is enforced.
Possible runtime effect
Loss of deterministic service for a safety-critical or system task.
Evidence
The requested TID is passed directly to sched_setattr(SCHED_EXT).
Required fix
Reject RT/deadline tasks by default and require an explicit, identity-bound eligible-task registration with rollback.

K0 K0-06 - Partial-switch starvation

Area
Fairness and admission
File / function
orchestra_scx_stage7.bpf.c struct_ops flags and local dispatch policy
Problem
Ext tasks can share CPUs with continuously runnable higher-precedence fair tasks.
Why it is wrong
No CPU isolation, service guarantee, or starvation monitor exists.
Possible runtime effect
ORCHESTRA task starvation followed by watchdog scheduler exit.
Evidence
SCX_OPS_SWITCH_PARTIAL is enabled and normal placement remains local.
Required fix
Enforce a controlled CPU/task admission plan and add bounded dispatch-delay monitoring and recovery before physical testing.

23. Final recommendation

QuestionIs this kernel prototype technically safe and algorithmically coherent enough for the first controlled real-machine test?
AnswerNo - not in its current state.

The userspace algorithm is coherent enough to continue engineering, and sched_ext fallback limits some worst-case effects. The bridge cannot yet prove immutable task ownership or coherent publication; migration can provoke scheduler failure; action semantics remain materially incomplete; and the canonical adaptive loop is disconnected from BPF.

Conditional next gate: after all K0 fixes, exact-kernel verifier/VM revalidation, and the dependency-ordered tests above, a first tightly controlled real-machine functional safety test would be reasonable. It would not yet justify performance, coordination, security, or deployment-readiness claims.

Scope: Linux sched_ext/eBPF implementation, directly relevant userspace bridge, canonical ORCHESTRA scheduling algorithms, and kernel/algorithm translation. Documentation quality, packaging, UI, game integrations, and benchmark presentation were excluded.

Primary repository sources: kernel/sched_ext/, kernel/sched_ext/bridge/, orchestra_paper_cpu_demo/orchestra_paper_cpu.c, and scheduler/algorithm tests. The source code governed implementation behavior; approved research definitions governed intended semantics.
