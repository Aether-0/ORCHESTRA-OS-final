This report separates attach success from action failure, names the most likely cause, and lists the exact continuation work.

1. One-page answer

Did it crash?
No
Clean unregister; sched_ext disabled at close
Did it attach?
Yes
After 7.0 port; 3/3 load cycles
Did actions work?
No
MIGRATE/SLEEP FAIL; RUN/YIELD/THROTTLE inconclusive

Why it failed: testers published directives to shell-loop worker TIDs that were mostly blocked waiting on child /usr/bin/sleep processes. Those children were never the map key. Global accepted then rose by one on the next trial, when the previous shell woke or exited. MIGRATE was additionally invalid: affinity CPU 0 vs target CPU 3. Per-task telemetry vanished in ops.disable when the short worker died. Silent load_directive() rejects (NO_DIRECTIVE, unstable snapshot, bad ABI) have no dedicated counters, so “error counters = 0” was misread as a clean miss rather than “not observed.”

What to fix to continue: a compiled long-lived worker with one TID; poll until that identity’s generation and accepted move; MIGRATE with affinity {0,3}; keep the task alive until per-task telemetry is dumped; add reject-reason counters. Do not apply the VirtualBox partial-switch / ENQ_LAST “P0 ownership” patch as the Kali fix. Do not boot the in-tree 6.12.96 bzImage (NVMe disabled). Do not claim paper Q, HMAC Signal Bus, predictor, or controller from this host.

4. Causal chain (ordered)

6.12 VM gate passed
Host is Kali 7.0 not 6.12
Port kfuncs + DSQ enums
Attach / full-switch / unload
Published TID not the scheduled worker
  1. Environment: physical host runs 7.0.12; prototype comments and VBox gate are 6.12 scx_bpf_dispatch*.
  2. Toolchain: first campaign lacked bpftool/libbpf-dev/kernel source. Authorized install unblocked compile.
  3. ABI: object built against 6.12 names failed ksym resolution on 7.0 BTF (F6).
  4. Runtime abort: insert wrappers without DSQ enum restore used DSQ id 0 (F7).
  5. Attach success: loader pins maps before attach; state enabled; switch_all=1.
  6. Wrong scientific question after that: system-wide running in the 10⁵ range proves full-switch, not that worker W executed action A.
  7. Action protocol error: workers changed from spin (skipped by SCX_OPS_ENQ_LAST) to sleep 0.01 loops. If that sleep is /usr/bin/sleep, each iteration is a new child TID. Publish keys the parent shell.
  8. Observation error: --status taken before the parent re-enqueues; per-task records deleted on exit.
  9. Second MIGRATE error: pin to CPU 0 then request CPU 3. Both bridge and BPF require the CPU in the allowed mask.
Residual hypothesis (only if a stable-TID retest still shows accepted=0 while the directive is listed): BPF task_identity(p) (tgid, pid, start_boottime) does not equal the enable-time identity the bridge uses as the hash key. Today that is not the best-supported explanation of the delayed-accept series.

Meanwhile system-wide enqueue rose into the tens of thousands and fallback ≈ running. That is expected for full-switch with almost no matching per-task directives. It is not proof that ORCHESTRA “did nothing”; it is proof that most tasks took the no-directive RUN fallback.

Contrast: exploratory 7-port ownership run published RUN to an admitted TID and saw accepted=11 dispatched=11 against running≈104k. Matching can occur; the later action campaign did not hold the right TID in the window.

8. What we have to fix and improve

Priority is scientific, not cosmetic. Do not start with performance ranking.

P0 — Required before the next Kali kernel claim

#Fix / improveWhyDone when
P0-1 Compiled worker, one stable TID, no /usr/bin/sleep. Use a busy-loop or builtin sleep in the same PID. Keep the process alive until telemetry is captured. Published identity must be the scheduled entity. ps shows one TID; identity map and directive key match that TID for the whole trial.
P0-2 Poll --status until that identity’s generation is visible and accepted (or a new per-TID counter) increases, then judge the action. Snapshot before publish, after accept, after dispatch, after effect. Delayed global accepted made the previous trial look like the current one. No one-test lag in the result table.
P0-3 MIGRATE protocol: affinity {0,3} (or full mask), start on 0, request 3. Prove mig_acc, mig_disp, per-task actual_cpu, and /proc/TID/stat PSR. Never taskset -c 0 vs target 3. Current FAIL is a mix of no accept and illegal affinity. CPU actually moves on ≥N agreed repeats (start with N=3, then 5).
P0-4 Add counters for every load_directive() miss: NO_DIRECTIVE, UNSTABLE_PUBLICATION, BAD_ABI, controller reject, plus existing stale/expired/bad_id/map_err. Print them in --status. Zero bad_id hid lookup misses. A miss names its reason.
P0-5 If P0-1…3 still show lookup miss: dump orch_identity vs orch_directives vs BPF task_identity(p) for the live TID (enable-time vs enqueue-time start_boottime). Residual identity-key bug. Bytes equal or a documented mismatch.

P1 — Kernel fidelity (needed for a true action claim, even after harness fix)

  • Prove isolated ownership on 7.0: either keep full-switch but attribute per TID, or partial-switch with explicit SCHED_EXT opt-in without forking workers. Gate every ORCHESTRA number on that TID’s enable/enqueue/running.
  • SLEEP: deferred ineligibility until not_before, then release via the pinned timer — not a short slice alias. Measure no execution in the sleep window.
  • THROTTLE: runtime budget over a period, not only a smaller slice. Measure duty cycle.
  • YIELD: queue-tail / min-slice semantics vs RUN, with yield_disp tied to the TID.
  • Keep 7.0 wrappers version-gated so 6.12 VM trees still build. Keep DSQ enum restore; do not use bare bpftool struct_ops register for this object (timer map + volatiles).

P2 — Test infrastructure (blocks science even when the BPF is right)

  • Make benchmark_suite.sh / full_compare.sh paths relative or honor ORCHESTRA_BPF/ORCHESTRA_BRIDGE. Stop hard-coding [LOCAL_HOME]/....
  • Do not run scripts that rm -rf /sys/fs/bpf/* on this host.
  • Memory stress: require stress (RAM), never dd onto a tmpfs smaller than STRESS_MB.
  • Kernel-health grep: ACPI BIOS Error matching BUG is a known false positive on this HP.
  • Thermal: do not start 24-way orchestra stress until short loaded runs stay well below package high (80°C observed nearby under CFS 60s).
  • Refresh docs/status/current-state.md: this box is i7-13700 / 24 CPU, not the older i5-10310U inventory; metal attach has now occurred.

P3 — After P0/P1 only

  • Matched CFS vs ORCHESTRA (optional scx_simple) with identical workers, duration, CPUs, N≥5, ownership proven.
  • Watchdog, unload-under-load, task-exit-during-directive, invalid CPU/PID (CLI already sampled).
  • Multicore scaling; NUMA is N/A (one node) for WP8 awareness.
  • Long-run only after short/medium loaded stability and thermal headroom.
  • Kernel Signal Bus / predictor / Q / controller remain NOT_IMPLEMENTED in BPF. Userspace work is a separate track.

9. Continuation sequence (next campaign)

Stop after any panic, repeated oops, hung-task/RCU stall caused by the test, or thermal approach to hardware critical. Preserve evidence. Do not edit production algorithms to force PASS.
  1. Confirm 7.0 object still loads: orchestra_loader --load → state=enabled → --unload.
  2. Start one compiled worker; record TID; dump identity map; publish RUN; poll until accepted for that identity; capture per-task tel before kill.
  3. Repeat for YIELD, then MIGRATE with legal affinity, then THROTTLE, then SLEEP with a legal not-before window.
  4. Only if P0-1…3 pass: isolated ownership vs full-switch documentation; then short loaded compare vs CFS.
  5. Leave WP2–WP6 kernel items BLOCKED until those subsystems exist in BPF.

Decision after a successful P0 retest: still KERNEL_PROTOTYPED, possibly EXPERIMENTALLY_VALIDATED only for declared actions on this host/kernel/workload/N. Never jump to DEPLOYMENT_READY.
